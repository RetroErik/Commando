# Commando 1.01 graphics analysis

**By Dag Erik Hagesæter / Retro Erik using Codex in VS Code** · [YouTube: Retro Erik](https://www.youtube.com/@RetroErik)

All offsets below are **file offsets in `COMMANDO.EXE`**. The MZ header is `200h` bytes, so the corresponding runtime IP within the load segment is file offset minus `200h`. `COMMANDO.DAT` contains an exact copy of the whole EXE starting at DAT offset `2000h`.

| EXE offset | Finding |
|---|---|
| `6C19h` | Push mode 4; the subsequent `6C1Dh` call selects CGA graphics via BIOS. |
| `54A9h` | Original clear of the RAM image used to build the static gameplay screen. It is unmodified in the current build. |
| `57E1h` | Original zeroing of AX after a pair of scrolling rows is composed. It is unmodified in the current build. |
| `6C49h`, `6C7Ch`, `77D7h` | `B800h` video segment setup. |
| `6CA2h` | Call to full-screen RAM-to-video copy; source is a 16 KB RAM segment. The patch replaces this call with its paired-plane transfer. |
| `6DBCh` | Call to direct-video object rendering at `77EAh`. The patch redirects it through the gap at `6E17h`. |
| `6DC3h` | Wrapper for the active-play renderer at `785Ch`, which draws into a RAM screen. |
| `77EAh` | Erases old object footprints, draws current objects, and updates each object's last-drawn fields in video memory. |
| `785Ch` | RAM-screen version of the same masked object drawing pass. |
| `7A99h` | Restores a sprite footprint from the background RAM segment. |
| `7E3Fh` | Masked sprite drawing. Each source byte is a mask/value pair; output is `(old & mask) | value`. |
| `7790h` | Clears a 16 KB RAM screen with one repeated byte. The call at `618Fh` clears the pre-play scene before static art is built; the patch replaces just that call with an equivalent clear and marks both video banks for a full transfer. |
| `77A6h` | `REP STOSW` inside the common screen clear. The patch replaces it with `INT 64h`, which preserves the RAM fill and clears the extra ColorPlus video bank for menus. |
| `63A5h` | Call to the common screen clear when the pre-play sequence ends. `INT 65h` performs the same RAM clear and removes old upper-bank soldier pixels. |
| `3601h` | Initializes state `02h` after the pre-play sequence. `INT 66h` performs the same write and enables coloring for that attract-play path. |
| `369Bh` | State `02h` back edge to `35C8h`. `INT 67h` disables recoloring and resumes at the original jump target. |
| `36B1h` | Sets state `04h` for the player-controlled round. `INT 68h` performs the same write and enables soldier coloring. |
| `36F7h` | State `04h` back edge to `358Ch`. `INT 69h` disables recoloring and resumes at the original jump target. |
| `79C1h` | CGA row-offset table lookup; even and odd scanlines use the standard `2000h` interleave. |
| `6E17h` | Nine zero alignment bytes after a return instruction. Six bytes hold `CALL 77EAh / INT 60h / RET`. |

The object array is a set of 8-byte records. The renderer reads sprite source offset from bytes 6–7; `FFFFh` means inactive. Current position is in bytes 2–3, while bytes 4–5 hold the last drawn position. The game initializes 25 slots. Slot 0 is not reliably the hero: it can hold the green soldier sprite at data offset `4D34h`. Sprite blocks contain an offset for the odd-x image, followed by height, byte width, and mask/value pairs. The `4D34h` sprite decodes to a 20 × 16 pixel figure using original color values 0, 2, and 3; no pixel geometry was edited.

The first patch colored after `77EAh`; the user's 86Box trace showed `mode=01`, `frames=0000`, `copy=65` during active play. The direct-video renderer hook was therefore not the gameplay path. The revised patch colored after the `6CA2h` RAM-to-video copy as well, selecting hero and enemy palettes by sprite source address. Known CGA-green enemy animation frames occupy data offsets `1E12h`–`3A0Eh`; known CGA-red hero frames occupy `3DACh`–`5848h`. The user's second 86Box screenshot exposed the earlier palette error: upper-bank pair value 2 produces blue there, while pair value 1 produces intensity. It also showed the soldier ranges had been assigned backward. The patch maps enemy source value 1 to blue, hero source value 2 to red, enemy yellow details to bright blue except for the white belt, and the hero's yellow belt row to black. The current palette makes the hero's other details white. The first recoloring pass rewrote the entire upper bank on every frame; incremental footprint restoration reduced that work, but the user still saw blinking. Moving the lower recolor before the copy did not fix the blink. The user's `Sprite IDs:` trace shows the observed hero and enemy frames fall inside the classified address ranges. A 16 KB upper-bank RAM shadow with scanline transfers eliminated blinking in 86Box, but the user saw brief original colors and slower play. Precoloring the copied EXE and DAT sprite values made play faster, but the user still saw delayed sprite colors with separate bank transfers. The current build transfers each changed pair of lower/upper words together and uses a RAM copy plus `REPE CMPSW` to skip unchanged lower-screen data. Its upper-color sprite copies are prepared at build time and painted into the shadow. The user confirmed that soldiers are visible during player gameplay in the earlier 52,112-byte build.

The MZ relocation entry at file offset `1Eh` covers the data-segment immediate at EXE offset `2A7h`. The data segment begins `8350h` bytes into the loaded image, and the EXE header occupies `200h` bytes, so EXE file offset = data offset + `8550h`. The enemy sprite region `1E12h`–`3B64h` maps to EXE `A362h`–`C0B4h`; hero `3DACh`–`599Eh` maps to `C2FCh`–`DEEEh`. The rock-like `739Ah` record maps to `F8EAh`; the `804Ah`–`84DCh` run maps to `1059Ah`–`10A2Ch`. The asset builder follows the odd-x offset in each frame header and edits only value bytes of mask/value pairs in both variants. These edited bytes are copied to the EXE embedded in DAT at file offset plus `2000h`.

The original screen clear at `7790h` is called from six places, all with a zero fill byte. The `618Fh` call sits in a pre-play setup immediately before static graphics are drawn. The paired-transfer build kept a RAM copy of the last lower video bank. On the user's second gameplay start, the score and side decoration disappeared: this is consistent with another game path changing video RAM while the saved copy still said those pixels were present. The `INT 63h` hook at `618Fh` performs the same 16 KB clear and marks the next transfer as full. A synthetic test deliberately erases video RAM while preserving the saved copy, then confirms that the scene reset restores it. The user confirmed this restored the decoration but reported blue enemy remnants in the menu. The `INT 64h` hook replaces the common clear's `REP STOSW` for other screens, preserves the original RAM clear, and resets the upper video bank to black. The user's trace showed five such clears, but soldiers still appeared in the menu, so the copy hook was likely repainting them from stale object records afterward. A broad gameplay flag set at `INT 63h` and cleared on every `INT 64h` removed menu remnants but also removed enemies in active play and introduced hero artifacts. The user's failing trace had two scene builds and three other clears. A narrower flag cleared at `63A5h` also removed enemies in play. Disassembly of the main game-state loop shows why: routine `6180h` is a pre-play sequence called at `35D2h`; its `63A5h` clear occurs **before** either play-state loop. State `02h` enters at `3601h`, but the user's next 86Box trace recorded only one start there while enemies remained absent in player gameplay. The main player loop is state `04h`, initialized at `36B1h`. The patch enables coloring at both entries and disables it on their respective back edges, while preserving each original write and jump. The latest patch also clears both video banks at those back edges before menu drawing; the synthetic DOSBox test confirms both hooks clear the banks and resume at the original targets. The F1 and game-over paths still need an 86Box visual check.

The gameplay screen builder at runtime `5239h` clears a separate 16 KB RAM image at `52A9h`, then draws scenery and frames. A prior experiment filled the playfield in that RAM image, but the game then copied its separate scrolling-ground buffer over the fill. `5B05h` constructs this 56-byte-wide by 128-row buffer at data offset `DCE2h`, and `5C7Fh` copies it over the playfield through `7AD1h`. The first attempted ground-row patch colored alternating scanlines because `5930h` fills the two scanlines separately at EXE offsets `5776h` and `5799h`. Coloring both rows produced solid brown but erased most palms: the tree renderer at `635Dh` ORs its pixels into the ground, and an all-ones fill prevents these pixels from changing. Recoloring the rows later restored palms, but the user observed missing bullets and incorrect sprite appearance under palms. The current build restores the original instructions at `54A9h`, `5776h`, `5799h`, and `57E1h` in both copied game files. Background color-0 pixels are black across the whole screen; separate palette processing handles selected objects and screen art.

The palette extension changes the copied `804Ah` projectile to white, `739Ah`, `8478h`, and `84AEh` rock-like records to dark/light gray, and the `8058h`–`83F4h` effects to dark red, yellow, and light gray. It does not alter the `7F74h` mixed-color item or `84DCh` jeep. The loader recognizes these records by their source offsets and paints their precomputed high-bank assets before paired transfer. For side art, it maps original red pixels to dark red and original green pixels to brown only in x byte columns 0–10 and 69–79. This transform runs once on the freshly built scene so subsequent copies do not remap transformed pixels. For dark-cyan frames and score text, it maps original color-3 pixels to lower-bank green plus upper-bank blue at fixed screen coordinates. The full-screen pass occurs after a scene reset; changed score words are updated before transfer on later frames. The five small life marks left of the life count occupy x byte 40–59 and y161–191; copying their lower pixel pairs to the upper bank was the first attempt to brighten them. The larger soldier icon at x byte 60–65 and y161–179 keeps its lower-bank colors, and its upper-bank bits are cleared; score digits below y180 remain cyan. The user's screenshots show that the marks are still mostly dark. A later fixed rectangle pass over `B800` and `BC00` did not repair them and slowed gameplay, so it was removed. The present diagnostic samples 16 fixed score-panel offsets in both video banks after the copy and direct-render hooks. Its `PLTRACE.TXT` result will identify which pixels and plane are missing on actual ColorPlus emulation. The first 86Box view exposed a coordinate error that left upper and score frame bars brown; the row fix made those bars cyan. A narrower side-art range corrected green vertical frame edges, which the user confirmed in 86Box.

The original `STARTC.COM` executes `COMMANDO.EXE` with DOS function `4B00h` at COM offset `66h`, then unconditionally exits with code zero. This hides a DOS load failure. The `run/STARTC0.COM` copy replaces that call with an appended diagnostic routine that forwards a load error as `80h + DOS error` and forwards the game's own return code after a successful launch. It also explicitly sets `ES:BX` to its EXEC parameter block. The original launcher contains `Commando crack by Demonlord 05/30/99...` at COM offset `C5h`. Its output string is terminated at the first byte in the patched copy; the preceding DOS interrupt instruction is retained. This avoids attributing later work to the author of that historical launcher. The original remains unchanged. The message alone does not establish who first cracked the game.

The four title bitmap records at EXE file offsets `1B46h`–`350Bh` contain CGA red, brown, and green pixels that produce multicolored logo artifacts in RGB ColorPlus output. The first menu patch mapped all opaque pixels to lower-bank value 2; the user observed an all-red logo, showing that value 2 is red in this game's selected CGA palette. `menu_assets.ps1` now keeps their masks and dimensions, retains red value 2 and green value 1, and maps brown value 3 to green value 1. The adjacent menu soldier record uses the same brown-to-green change. The patcher also changes 21 verified menu and high-score text color arguments from CGA brown value 3 to green value 1. These byte changes are made identically in the copied EXE and the EXE embedded in copied DAT. They do not affect the active-play soldier frames. Light-red logo accents would need ColorPlus upper-bank drawing during the menu and remain an optional visual change.

The original launcher installs an INT 13h hook before DOS loads `COMMANDO.EXE`. The hook intercepts floppy drive 0 reads and serves bytes from `COMMANDO.DAT` using DOS file calls. On a real floppy A: drive, DOS's own file reads can also invoke INT 13h on drive 0. The code therefore appears able to intercept its own EXE load or recurse while reading DAT. The diagnostic copy gets the DOS busy flag pointer with function `34h` and chains busy-time floppy reads to the saved BIOS handler. Direct game reads continue through the original DAT hook. The copied launcher still performs its original interrupt cleanup. The source `Commando/STARTC.COM` is unchanged. [Microsoft's DOS system-call documentation](https://github.com/Microsoft/MS-DOS/blob/main/v2.0/bin/SYSCALL.DOC) identifies function `34h` as the DOS critical-section flag query. The user confirmed that the patched launcher now runs the game in 86Box from A:.

A later 86Box run of the enlarged recoloring loader returned `DOS EXEC failed: AX=000A` before reaching the copied launcher. Inspection found that the outer loader had left `ES` set by DOS interrupt-vector queries before calling DOS `4B00h`; its EXEC parameter block was in `CS`. The loader now sets `ES=CS` immediately before EXEC. The user confirmed the revised loader starts gameplay in 86Box.

## Evidence and limits

- Original EXE SHA-256: `4F53975ABF756A27BA94713C32134F501F5349A80798151E78666FA6A6D52D4E`.
- Original DAT SHA-256: `E92EC0D64715DEADA88495E5415634FDE05B155C3EDEDAE2B0E00844A26AAAE9`.
- `build.ps1` and `test.ps1` completed on the development machine. The DOSBox smoke tests confirmed the mode, RAM copy, pre-play clear, other-screen clear, both play-state entries, and both state-loop exits; they checked the black hero belt, blue enemy body, white enemy detail, restoration of the old position of a moving enemy, an unrelated lower-screen change, restoration after a simulated video-memory reset, recoloring after a clear during play, and the original branch targets at both state exits.
- A local DOSBox launch of the current copied game remained active for 12 seconds. Its trace reached DOS EXEC; this is only a startup check because DOSBox does not display ColorPlus colors.
- An initial local DOSBox game run and an untouched baseline both stayed active for 20 seconds. The loader trace reached DOS EXEC; neither run returned to the DOS prompt during that interval. This does not explain the early exit reported on another setup. `PLTRACE.TXT` now records DOS startup errors or child return status for that case.
- A local DOSBox test with `COMMANDO.EXE` deliberately absent returned `code=82`, confirming that the diagnostic launcher exposes DOS error 02 through the outer trace.
- The untouched game exited early from A: in the user's 86Box configuration; the repaired copied launcher now loads active gameplay there.
- The copied game was launched in DOSBox, but a visual capture was unavailable because the Windows computer-use helper could not connect. DOSBox does not emulate ColorPlus colors in any case.
- The user confirmed the paired-transfer build produced stable red and blue soldiers in 86Box. An earlier build left soldier pixels briefly in the menu until the high-score screen cleared them; the user confirmed the latest F1 exit leaves the menu clean. The brown-ground experiment showed striped rows, missing palms, lost bullets, and sprite artifacts where soldiers overlapped scenery. The experiment was removed at the user's request. The user confirmed that the restored black-background build looks correct in 86Box and that dark-red/brown side art and dark-cyan score look good. The current 55,040-byte diagnostic build passes the DOSBox memory tests and has been byte-verified in the EuroPC floppy image. The life marks still need a correction informed by actual ColorPlus video bytes. The corrected green menu pixels, exact projectile and effect colors, and physical ColorPlus hardware remain untested.

Hardware control was checked against the [Paradise PVC4 ColorPlus-compatible register description](https://bitsavers.trailing-edge.com/components/westernDigital/_dataSheets/PVC4.pdf) and the [Color Graphics Adapter Notes](https://www.seasip.info/VintagePC/cga.html#plantronics).
